# Электронный дневник

Портал электронного дневника колледжа: дневник студента, журнал старосты,
студия преподавателя и панель разработчика. Node.js без внешних зависимостей.

## Быстрый запуск

```bash
# 1. Задайте переменные окружения (регистр логина не важен, символов в пароле >= 12)
DEV_LOGIN=admin DEV_PASWORD="moy-dlinnyy-parol" npm start

# либо создайте файл .env (см. .env.example) и просто:
npm start
```

Откройте http://localhost:3000 и войдите под данными из `DEV_LOGIN` / `DEV_PASWORD`.
Дальше в **Студии Plus** создайте аккаунты преподавателей, старосты, куратора и дежурного администратора.

> Приложение слушает внутренний порт **3000**. Если видите `EADDRINUSE`,
> остановите другой процесс, который уже занял этот порт.

Новая установка запускается полностью пустой: без тестовых студентов, расписания,
сетки звонков, оценок, посещаемости, ДЗ и мероприятий. Сохраняется только
аккаунт разработчика из окружения.

### Windows PowerShell

```powershell
$env:DEV_LOGIN="admin"; $env:DEV_PASWORD="moy-dlinnyy-parol"; npm start
```

## Превью ссылки в Telegram и соцсетях

В `index.html` и `login.html` добавлены Open Graph-теги: при вставке ссылки в чат Telegram
появляется карточка с картинкой (`og-image.png`, 1200×630), названием и описанием.
Сервер сам подставляет абсолютный адрес сайта по заголовку `Host` / `X-Forwarded-*`.
Если сайт стоит за прокси с нестандартными заголовками, задайте `PUBLIC_URL=https://ваш-домен`.

Telegram кэширует превью. Если ссылку уже отправляли раньше, обновите кэш через
бота [@WebpageBot](https://t.me/WebpageBot): отправьте ему ссылку на сайт.
Превью работает только для публичного адреса (HTTPS-домен, не `localhost`).

## Заставка при запуске приложения

При запуске сайта как установленного приложения (с экрана «домой») показывается анимированная
заставка (`splash.js`): рисуется иконка календаря, загорается «живая» точка, появляется название.
Она идёт около 2,5 секунды, показывается один раз за запуск приложения и пропускается тапом.
В обычной вкладке браузера её нет. Для просмотра в браузере добавьте к адресу `?splash=1`,
например `/login.html?splash=1`. При включённом «уменьшении движения» в системе показывается
короткая версия без анимаций. Системный экран загрузки (до открытия страницы) задаёт сама ОС
из иконки и `background_color` манифеста — анимировать его нельзя.

## Сезонное оформление (Хэллоуин)

Один файл пары `theme.css` + `theme.js` подключён на всех пяти страницах и отвечает за
праздничную тему. Обычные цвета берутся из CSS-токенов (`--g1`, `--g2`, `--glow`, `--acc`),
поэтому для перекраски всего портала достаточно поменять их в `html.halloween` — новых
картинок в проекте нет, вся графика (луна, нетопыри, паутина, тыква, туман) собрана из CSS и SVG.

- **Когда включается.** Автоматически с 20 октября по 1 ноября включительно, по дате устройства.
- **Ручной переключатель.** Дневник → «Аккаунт» → «Настройки» → «Внешний вид» →
  «Праздничное оформление»: `выкл` / `авто` / `вкл`. Выбор хранится в `localStorage`
  под ключом `sd_season` и действует только на этом устройстве.
- **Проверка на любом числе.** `?halloween=1` включает тему принудительно, `?halloween=0` —
  выключает, не трогая сохранённую настройку.
- **Мелочи.** Цвет системной шапки (`theme-color`) и заставка PWA подхватывают сезон;
  декор живёт внутри анимированного фона, поэтому переключатель «Анимированный фон» выключает
  и его; при системном «уменьшении движения» анимации нетопырей, тумана и углей отключаются.

Чтобы добавить другой сезон, скопируйте блок `html.halloween` в `theme.css`, декор в
`theme.js` и окно дат в функции `inSeason`.

## Важно о входе

- Логин **не чувствителен к регистру** — сервер приводит его к нижнему регистру.
- Пароль берётся **ровно так, как задан** (плюс обрезаются пробелы по краям).
- Сессия живёт 30 дней и продлевается при активности (cookie `SameSite=Lax`, чтобы вход не терялся
  при открытии сайта по ссылке из Telegram и в установленном PWA).
- Cookie сессии становится `Secure` только при HTTPS. По `http://localhost` всё работает,
  даже если `NODE_ENV=production`.
- При смене переменных окружения сервер нужно **перезапустить**.

## Расписание

Расписание задаётся **типовой неделей** (Пн–Вс) и повторяется каждую неделю автоматически,
начиная с `SCHEDULE_START` (по умолчанию 19 октября 2026). Листать можно сколько угодно вперёд
(до ~10 лет): в дневнике — стрелками, свайпом или кнопкой «Сегодня», в журнале и студии — стрелками ‹ › по неделям.

- Оценки, посещаемость, ДЗ и мероприятия хранятся **по конкретным датам**. Номер дня в ключах
  (`день:пара:студент`) — число дней от даты старта, поэтому у каждой недели свои данные.
- Правка пары в журнале меняет типовую неделю: изменение действует на все такие дни недели.
- Типовая неделя и звонки принадлежат **группе** (`group.schedule`, `group.times`): у разных групп
  они свои. `DB.sch` и `DB.times` — запасной вариант для аккаунтов без группы.
- Преподаватель может ставить оценки и отметки только **сегодня** и только на своей текущей паре.
  ДЗ можно выдавать на любую дату.

### Импорт расписания из Excel

Журнал → вкладка «Расписание» → «Импорт из Excel». Принимаются `.xlsx`, `.xls`, `.csv`.
Кнопка «Скачать шаблон» даёт готовую таблицу с инструкцией.

| Столбец | Обязателен | Пример |
|---------|------------|--------|
| День недели | да | `Понедельник`, `Пн`, `1` (если день повторяется подряд — можно только в первой строке) |
| Пара | да | `1` … `12` |
| Предмет | да | `Математика` |
| Преподаватель, Кабинет, Корпус | нет | `Иванов И. И.`, `204`, `Корпус А` |
| Тип | нет | `Лекция` / `Практика` (по умолчанию практика) |
| Начало, Конец | нет | `09:00`, `10:30` — обновят сетку времени пар |

Заголовок может быть не в первой строке; названия столбцов распознаются по синонимам
(«Дисциплина», «Аудитория», «№ пары» и т. п.). Перед применением показывается предпросмотр
с найденными парами и списком пропущенных строк. Импорт **заменяет** типовую неделю целиком.
Файл разбирается в браузере библиотекой SheetJS, которая подгружается с `cdn.sheetjs.com`;
CSV читается без неё (в том числе в кодировке Windows-1251 и с разделителем `;`).

## Дневник студента

Четыре вкладки внизу: **Дневник**, **Рейтинг**, **Чаты**, **Аккаунт**.

- **Отметки посещаемости** показываются там же, где оценки: цветная буква в карточке пары
  (`У` — уважительная, `Н` — неуважительная, `О` — опоздание, `Б` — больничный) с подписью,
  а на экране пары — отдельный блок с расшифровкой и минутами опоздания. Дневник показывает
  только личные отметки: у преподавателя и куратора в данных вся группа, им показываются сводки в журнале.
- **Состоявшиеся пары приглушены** — серая плашка номера и бледная карточка. За прошедший день
  в шапке появляется метка «прошедший день», а завершившиеся сегодня пары получают «завершена»;
  текущая пара остаётся зелёной с полоской прогресса.
- **Рейтинг** — вкладки нет в старом дневнике, она новая: место, балл, средний балл оценок и
  посещаемость по группе. Сортировка по баллу / оценкам / посещаемости / фамилии, пьедестал для
  первых трёх, своя карточка позиции у студента и сводка группы у куратора и преподавателя.
  Строку можно раскрыть — там распределение оценок и счётчики `У`, `Н`, `О`, `Б`.
- **Чаты** — общий чат группы плюс личные диалоги; непрочитанные сообщения видны цифрой на вкладке.

### Как считается балл

`балл = 0.6 × балл успеваемости + 0.4 × балл посещаемости` (каждый в процентах):

- успеваемость: `(средний балл − 2) / 3 × 100`, то есть пятёрка — 100, четвёрка — 66.7, тройка — 33.3;
- посещаемость: `100 − (взвешенные пропуски / отмеченные пары) × 100`, веса `Н` = 1, `О` = 0.5,
  `У` = 0.25, `Б` = 0; «отмеченные пары» — те, где посещаемость проставили хотя бы одному студенту;
- если оценок или отметок нет, считается только по доступной части, и такой студент идёт ниже тех,
  у кого данные полные (в списке помечено «оценок нет» / «посещаемость не учитывалась»).

Все расчёты — на сервере в `ratingOf()` (`/api/rating`): наружу уходят только средние баллы и
счётчики, отдельные оценки одноклассников не передаются.

## Чаты

Чаты живут на отдельной странице **`chat.html`**, адрес диалога — `домен/chat/<код>`
(короткий код из символов без похожих пар `0/o`, `1/l/i`, чтобы его можно было продиктовать).
Вкладка «Чаты» в дневнике ведёт сюда же; сама переписка в дневнике не открывается,
и поле ввода видно только внутри диалога. Сообщения хранятся в `DB.chats` этого же файла базы.

- **Общий чат группы** существует у каждой группы автоматически (`id` вида `g:Название`).
  В нём пишут студенты, староста, куратор группы и преподаватели, чей предмет стоит в её
  расписании. Внизу диалога подпись «Его увидят: …» — кому видно сообщение.
- **Личный диалог** (`id` вида `d:логин1~логин2`, логины в алфавитном порядке) создаётся кнопкой
  «Начать переписку»: в списке только те, с кем чат разрешён, и он фильтруется по фамилии,
  группе, предмету и роли.
- **Комната** — групповой диалог вокруг темы: кнопка «Создать комнату», заголовок и список
  участников. Её адрес `/chat/<код>` можно скопировать и передать участникам.
- **Кому доступен личный чат**: внутри одной группы (студент ↔ студент, студент ↔ свой куратор,
  студент ↔ преподаватель своих предметов) либо с дежурным администратором и разработчиком —
  они видят все чаты. Проверка `directAllowed()` на сервере; чужой диалог отдаёт `404`,
  попытка написать «через голову» — `403`.
- **Профили внутри чатов**: аватар или имя в сообщении открывают карточку человека
  (баннер, био, оформление, галочка, статус) с кнопками «Написать», «Скопировать ссылку»
  и «Заблокировать». Ссылка профиля — `домен/chat/?user=<логин>`.
- **Блокировка** убирает переписку из списка, запрещает обоим писать и прячет человека
  из контактов; заблокированные показаны отдельным списком, где их можно вернуть одним нажатием.
  История сообщений при этом сохраняется.
- **Закрепление** — личная настройка каждого участника (`chat.pins[login]`): закреплённые диалоги
  поднимаются наверх у того, кто их закрепил, и не трогают список собеседника.
- **Панель эмодзи**, правка и удаление своих сообщений (админские роли могут убрать чужое),
  удаление помечается как «сообщение удалено», правка — как «изменено».
- **Непрочитанное** считается по метке `chat.reads[login]`; она обновляется, когда диалог открыт,
  поэтому цифры на вкладке исчезают сами. Открытый диалог подтягивает новые сообщения каждые 5 секунд,
  а счётчик в заголовке вкладки — раз в минуту.
- **Пуш приходит только из личного диалога** (тип «Личные сообщения» в настройках): спамить
  уведомлениями всей группы из-за каждого сообщения не будем. Клик по уведомлению открывает
  нужный `/chat/<код>`.
- Ограничения: 2000 символов в сообщении, не чаще одного сообщения в секунду, в чате храним
  последние 300 сообщений. Текст экранируется на клиенте, HTML в сообщении не исполняется.

При удалении аккаунта его личные диалоги удаляются, при удалении группы — её общий чат.

## Push-уведомления

Настройки: дневник → колокольчик → «Уведомления». Включение действует **на конкретном устройстве**
(браузер попросит разрешение), типы уведомлений хранятся в аккаунте.

| Что приходит | Кому | Условие |
|--------------|------|---------|
| Новая оценка | студенту, которому поставили | сразу |
| Новое ДЗ | студентам и старостам | сразу, с текстом и сроком |
| Изменение расписания | всем, кроме автора правки | одним сообщением после паузы 90 с |
| Новое мероприятие | студентам и старостам | по умолчанию выключено |
| Личное сообщение | собеседнику в личном диалоге | сообщения общего чата группы не рассылаются |
| Напоминание о паре | студентам; преподавателям — о своих парах | за 10 / 30 / 60 мин; для подряд идущих пар (перерыв меньше 40 мин) не дублируется |

«Не беспокоить ночью» (22:00–07:00 по времени сервера): уведомления откладываются до утра,
напоминания о парах в это время не отправляются. Часовой пояс задаётся переменной `TZ`.

**Требования.**
- Сайт должен работать по **HTTPS** (на `localhost` работает и по HTTP).
- **iPhone/iPad** (iOS 16.4+): сначала «Поделиться» → «На экран Домой», затем открыть дневник с иконки.
- Задайте `VAPID_SUBJECT`: часть push-сервисов отклоняет запросы без корректного контакта.
- Ключи VAPID создаются автоматически и хранятся в файле базы (`data/data.json`). **Не удаляйте его**: после потери ключей
  подписки на устройствах станут недействительными, и уведомления придётся включить заново.

**Как это устроено.** Сервер отправляет push-сервису (Google/Mozilla/Apple/Microsoft) пустой сигнал,
подписанный VAPID; сервис-воркер `sw.js` получает его, забирает текст у вашего сервера
(`POST /api/push/pending`) и показывает уведомление. Текст не проходит через сторонние сервисы.
Сервер отправляет сигналы только на адреса известных push-сервисов (защита от SSRF).

## Профили, оформления и награды

У каждого аккаунта есть профиль: **био, аватар, баннер, оформление, галочка
«проверенный» и мелкий статус рядом с ником** (эмодзи или маленькая картинка —
хоть анимированная GIF). Профиль редактируется в дневнике: вкладка «Аккаунт» →
«Настроить профиль» (или ссылка `diary.html#profile`). Картинки сжимаются в браузере
(аватар и статус до 400 КБ, баннер до 900 КБ) и складываются в `data/media/` —
вместе с базой они переживают обновление кода. GIF сервер не перекодирует, анимация сохраняется.

**Оформления (цветовые темы).** Общедоступны ровно три: «Аврора», «Океан» и «Закат» —
они есть у всех. Остальные эксклюзивные и выдаются только разработчиком:

| Код | Название | Как выдаётся |
|-----|----------|--------------|
| `rose` | Розовые тона | Студия Plus → «Награды» |
| `crimson` | Чёрный с красным | Студия Plus → «Награды» |
| `gold` | Золотой резерв | Студия Plus → «Награды» |
| `acid` | Кислотный неон | Студия Plus → «Награды» |

Студия Plus → вкладка **«Награды»** → человек → карточка оформления (замок ↔ галочка).
Там же выдаётся и снимается галочка «проверенный» и ставится эмодзи статуса.
Снять выдачу можно в любой момент: если студент уже включил это оформление,
его вернёт на «Аврору». Выбор темы хранится и в профиле (`profile.design`), и локально
в браузере (`localStorage`), поэтому переключение мгновенное и не зависит от скорости сети;
чужое или снятое оформление сервер не примет — `PUT /api/profile` отвечает `403`.
Реализовано токенами в `theme.css` (`html[data-design="…"]`), новых картинок не появляется.

**Приватность оценок.** Оценку видят только: выставивший её преподаватель (или тот,
кто внес её через журнал/студию), куратор группы, дежурный администратор, разработчик
и сам студент. Одноклассники получают только свой балл и итоговый рейтинг —
в `/api/state` чужие оценки просто не попадают, а не прячутся на клиенте.
Кто выставил оценку сохраняется в `DB.gradeMeta`, поэтому журнал показывает автора,
а преподаватель не может снять чужую отметку. `PUT /api/state/grades` работает как
точечная правка: приходят только изменённые ключи, `null` снимает оценку, остальное не трогается.

## Сохранение после перезапуска

**Живая база не лежит в дереве репозитория.** По умолчанию это `data/data.json` рядом с
`server.js`, а не `./data.json` в папке кода. Поэтому `git pull`, `git checkout -- .`,
`git clean -fd` или чистое клонирование поверх той же папки не могут перезаписать данные —
в `.gitignore` и `.dockerignore` каталог `data/` исключён. Старый `./data.json`, если он
остался с прошлых запусков, сервер сам переносит в `data/` при старте (копирует, оригинал не трогает).

Что включено в защиту:

| Что | Как работает |
|-----|--------------|
| Атомарная запись | пишем во временный файл `<data.json>.<pid>.tmp` и переименовываем поверх; обрыв посреди записи не оставит half-written JSON |
| Резервные копии | перед записью (не чаще раза в 5 минут) предыдущая версия кладётся в `data/backups/data-< ISO-время >.json`, храним 36 последних |
| Самовосстановление | если `data.json` не читается, сервер поднимает последнюю резервную копию, а битый файл оставляет рядом как `data.json.corrupt-<дата>` — ничего не удаляется |
| Миграция схемы | `migrate()` только добавляет недостающее (поля аккаунта, `gradeMeta`, `chats`, коды чатов); существующие записи не переписываются |
| Демон-данные | вычищаются один раз и только из пустой базы: как только появился хотя бы один аккаунт, база считается рабочей |
| Медиафайлы | аватары и баннеры — в `data/media/`, то есть в том же постоянном томе, что и база |
| Права доступа | файл базы создаётся с режимом `0600`, каталоги `data/` и `data/media/` сервер делает сам |

`PUT /api/state/:part` принимает **точечные правки** (присылаются только изменённые ключи,
`null` снимает запись), поэтому сохранение половины журнала из студии не затирает чужие оценки и ДЗ.

Перезапуск Node.js ничего не сбрасывает. Путь можно вынести на постоянный диск через `DATA_FILE`:

```bash
DATA_FILE=/var/lib/e-diary/data.json npm start
```

Каталог должен существовать или быть доступен процессу на запись. Сервер создаёт
его автоматически, если у процесса есть права.

**Если добавляется новый статический файл** (страница, стиль, скрипт), его нужно дописать
в `COPY` в `Dockerfile` — иначе в образе его не будет, и приложение отдаст 404.

Для Docker используйте готовый `compose.yaml`:

```bash
cp .env.example .env
# отредактируйте DEV_LOGIN и DEV_PASWORD
docker compose up -d --build
```

Named volume `diary_data` хранит каталог `data/` (базу, резервные копии и медиа) отдельно от контейнера. Поэтому
перезапуск и пересоздание контейнера не удаляют данные. Не запускайте production
на эфемерной файловой системе без volume или постоянного диска.

## Поиск и устранение неполадок

**Контейнер перезапускается с `EADDRINUSE: address already in use`**
Порт уже занят другим процессом. Строка `HTTP server started on port…` в логе
печатается **не этим приложением**: наш сервер выводит
`Электронный дневник: http://…`. То есть порт держит чужой сервис или агент
платформы, запущенный раньше нашего процесса.

1. В панели хостинга выставьте внутренний порт приложения **3000**.
2. Остановите предыдущий контейнер/деплой этого же проекта:
   ```bash
   docker ps
   docker stop <container-id>
   # или: docker compose down, затем docker compose up -d --build
   ```
3. Внутри контейнера найдите процесс: `ss -ltnp | grep 3000`.
4. Убедитесь, что платформа не запускает второй HTTP-сервер вместе с `npm start`.
5. Проверка синтаксиса перед деплоем: `npm run check`.

Текущая версия выполняет одноразовую миграцию старой демонстрационной базы на
чистую схему версии 4. После первой записи последующие перезапуски базу не очищают.

## API (кратко)

- `POST /api/login` — вход по логину/паролю, сессия в HttpOnly-cookie
- `POST /api/register` — самостоятельная регистрация студента
- `POST /api/logout` — выход
- `GET /api/me` — текущий пользователь
- `GET /api/state` — состояние (типовая неделя `sch`, дата старта `start`, оценки, посещаемость, ДЗ, события, сетка времени). Оценки отдаются с учётом приватности: только свои, куратору — вся группа, автору правки — его; поле `gradeMeta` говорит, кто выставил оценку
- `GET /api/rating` — рейтинг группы: место, средний балл, счётчики `У`/`Н`/`О`/`Б` и итоговый балл (только агрегаты, без чужих оценок)
- `GET /api/chats` — мои чаты (последнее сообщение, счётчик непрочитанного, закрепление), список тех, с кем разрешён личный диалог, заблокированные и каталог оформлений; `POST /api/chats { to }` — создать личный диалог и получить его код
- `GET /api/chat/:код` — сообщения диалога (`?after=ts` — только новые) и его участники; `POST /api/chat/:код { text }` — отправить сообщение
- `PATCH /api/chat/:код/сообщение/:id { text }` — правка своего сообщения, `DELETE` — удаление; `POST /api/chat/:код/pin { pinned }` — закрепить/открепить для себя
- `POST /api/rooms { title, members, first? }` — создать комнатный диалог с несколькими участниками
- `POST /api/block { login, unblock? }` — заблокировать или разблокировать пользователя
- `GET|PUT /api/profile` — свой профиль (био, аватар, баннер, оформление, статус); `POST /api/profile/media { kind, data }` — загрузка картинки (avatar / banner / status), `GET /api/profile/:login` — карточка другого человека
- `POST /api/accounts/:login/grant { design, grant, verified, statusEmoji, statusMedia }` — выдача эксклюзивного оформления, галочки и статуса (только разработчик)
- `PUT /api/state/:part` — изменить часть (`grades`, `att`, `hw`, `sch`, `ev`, `times`) с проверкой прав; принимаются только изменённые ключи, `null` снимает запись
- `GET /api/push/config`, `PUT /api/push/prefs`, `POST /api/push/subscribe|unsubscribe|test` — push-уведомления; `POST /api/push/pending` — забирает уведомление сервис-воркер
- `POST /api/schedule/import` — атомарный импорт типовой недели `{ sch, times? }` (право `schedule`, для `times` — ещё и `times`)
- `GET|POST /api/accounts`, `PATCH|PUT /api/accounts/:login`, `DELETE /api/accounts/:login` — управление аккаунтами (только разработчик)
- `GET|POST /api/groups`, `DELETE /api/groups/:id` — учебные группы (их расписание и звонки хранятся внутри группы)

Все изменяющие запросы проходят проверку по серверной матрице прав,
курсоре/предметной принадлежности и текущей паре для преподавателя.


## Чистая база и сохранение на Bothost

В комплекте находится пустой `data.json`: тестовые аккаунты, расписание, оценки, посещаемость, домашние задания и мероприятия удалены. При запуске сервер создаёт системный аккаунт разработчика из `DEV_LOGIN` и `DEV_PASWORD`; он нужен для входа и ручного создания новых аккаунтов. Оставлена одна пустая группа `02-СД-25-о`, чтобы можно было сразу создать первые аккаунты студентов/куратора/старосты. Первая база создаётся в `data/data.json` (см. «Сохранение после перезапуска»).

Сервер сохраняет изменения синхронно в путь из переменной окружения `DATA_FILE`. Если на Bothost в логах указан `/app/data/data.json`, именно этот путь является активной базой. **Замена `data.json` в папке проекта не сбрасывает отдельную базу по `DATA_FILE`.** После развёртывания войдите под разработчиком и используйте в панели разработчика кнопку «Полностью очистить базу»: она очищает активный файл базы, оставляя только аккаунт разработчика и одну пустую группу.

Чтобы данные переживали перезапуск, каталог `/app/data` должен быть постоянным томом/хранилищем Bothost. Само приложение уже создаёт каталог и файл при запуске, если у процесса есть права записи; если Bothost удаляет `/app/data` при пересоздании контейнера, нужно включить постоянное хранилище в настройках хостинга.
